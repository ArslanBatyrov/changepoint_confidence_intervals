## 1. Project goals

The problem I was faced with was that when standard PELT is used to detect a
changepoint we get one number, the best response. However, we do not get an
understanding of the uncertainty of the given answer. For example, how close were
other options? Which other segmentations at a given confidence level are plausible?
Furthermore, what even were the alternative segmentations? These questions could be
answered by having a built in confidence set.

Owen, my mentor, already had the prototype ready and the way of getting a confidence
set for PELT ([his prototype], `PELT_CS_fns.R`, together
with the [list of desirable properties] a confidence set
should satisfy). My task was to port this code, make it generic for all distributions,
and make it easily accessible by exporting the functions and documenting them.

So the entire method comes from my mentor Owen. I only made an attempt to bring it to
production, with a generalised core in R, a public API, and so on.

## 2. What was built

The feature is complete and working end to end for PELT. A user writes:

```r
library(changepoint)

set.seed(1)
x   <- c(rnorm(100), rnorm(100) + 1.5, rnorm(100) - 1)  # true changes at 100 and 200
fit <- cpt.mean(x, method = "PELT")
cpts(fit)                          # 100 203  <- the single best answer misses 200

fit <- confidence_set(fit, level = 0.95)
conf.set(fit)[["0.95"]]
```

and gets:

```
Confidence set (level = 0.95)

Optimal changepoints:
  100 203 300

Alternative segmentations (13), extra cost vs optimal (budget 13.93):
  100 200 300       +0.01
  101 203 300       +0.29
  103 203 300       +1.78
  100 202 300       +1.80
  ...
  100 200 203 300   +13.75
```

Three things I want you to pay attention to:

* **The single point estimate missed the actual changpoint at 200 (because it was so close to 203)! yet, the conf - set caught ** The true second change is at 200.
  PELT alone said 203. The confidence set contains the true segmentation at an extra
  cost of only +0.01, a statistical dead heat.
* **Uncertainty in the number of changepoints.** The last row has three changepoints
  where the optimal has two. This is why we need a set of whole segmentations. A set of whole
  segmentations can display an alternative that has more or less changepoints.
* **Each alternative carries a gap!(feature I like the most)**, its extra cost against the optimal, and the set
  carries the budget the gaps live inside. Alternatives print most plausible first.

What shipped:

* `confidence_set(fit, level)` and `confint(fit, level)`: two names, in reality one engine. We made it so that the people whoa re used to confint can also easily use our package. QUESTION: Shall we rename conf_set to confset? 
  Then results are stored in a new `conf.set` slot on the `cpt` class, keyed by level, so
  several levels can accumulate on one fit and nothing is overwritten.
* A slot level cache: the expensive part (re running PELT with capture on) is level
  free and runs once; every further level reuses it and is nearly free.
* Questionable in reality: All PELT cost functions are supported: Normal (mean, variance, mean and variance),
  Exponential, Gamma, Poisson, each with or without MBIC, 12 in total, through one generic core with no per distribution branches. 
  But all of the cs files built on the assumption of the Normal Dist. Thus, other distributions might need some tweaks to be made, we discussed it with Owen and Rebecca, they said they will amke the tweaks after the GSoC ends.
  
* A print method with gap sorted alternatives, a soft display cap
  (`options(changepoint.confset.n = ...)` or `print(x, n = Inf)`), and a whole slot
  print that shows every stored level in order.
* The normal PELT path is untouched: with `conf.set = FALSE` (the default) the C
  engine produces byte identical output to the released package.

## 3. How it works

Three pieces, in the order the data flows.

### 3.1 The C capture

PELT's C engine keeps a "checklist" of candidate last changepoints and prunes it
every iteration; the near misses it discards are exactly what a confidence set is
built from. I extended
[`PELTC`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/src/PELT_one_func_minseglen.c)
with four new arguments (an on/off switch, two output buffers, and a size handshake;
registration updated from 11 to 15 arguments in
[`changepoint_init.c`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/src/changepoint_init.c#L20)).
When the switch is on, the engine runs normally and then
[**replays the forward pass**](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/src/PELT_one_func_minseglen.c#L221-L287),
saving the surviving candidates at each optimal changepoint. A replay is used because
the optimal changepoint times are only known after backtracking; a second linear pass
costs time but avoids storing a checklist at every time point.

The confidence set math needs each candidate's cost *without* penalties. Instead of
tracking a second cost array in C (as the research prototype does), I derived that the
pure cost can be recovered from values the engine already has:

```c
checklist_likes[i*rowcap + r] = tmplike[i] - numchangecpts[checklist[i]]*(*pen);
```

because the penalised cost of a path through candidate `cl` contains exactly
`numchangecpts[cl]` penalties (the seed `-pen` and the new changepoint's `+pen`
cancel). One line instead of taking extra memory.

### 3.2 The memory contract

C cannot return variable sized grouped results, and R cannot know the needed size
before PELT runs. The solution, suggested by Rebecca: R pre allocates a **matrix**
(one row per optimal changepoint, one column per candidate slot) and C fills it by
column major index, so the per changepoint grouping survives the C to R trip for
free. The size handshake `cs_dim` travels both ways: R sends the capacity it
allocated, C writes back the size it truly needed, and R
[re runs once with the exact size](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/PELT_one_func_minseglen.R#L33-L90)
if the first guess undershot. Also, importantly, to avoid the crash `tryCatch` around the reallocation acts as a
universal memory cap with a warning instead. This was done as an alternative that overall gives the same result as a 50% RAM warning that we were thinking about at the beginning.

### 3.3 The R core

The set itself is computed in pure R in
[`R/conf_set.R`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/conf_set.R),
ported from the Owen' prototype and made generic: costs arrive already computed
from C and are never recalculated from a per distribution formula, which is what
lets one core serve all 12 cost functions.

* [`cs_penalty`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/conf_set.R#L236)
  turns the confidence level into a cost budget (the prototype's formula, unchanged).
* [`cs_core`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/conf_set.R#L249)
  keeps, at each boundary, every candidate whose cost is within the budget of the
  optimal, and records each candidate's gap.
* [`cs_backtrack`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/conf_set.R#L289)
  turns the kept positions into whole segmentations by walking PELT's backpointer
  table: freeze the optimal suffix, move one boundary to a candidate, rebuild the
  optimal prefix by backpointer walking. This is also where uncertainty in the
  *number* of changepoints appears, since a walk from a moved boundary can pass
  through more or fewer optimal changepoints.
* [`confidence_set`](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/blob/5d7851f/R/conf_set.R#L8)
  ties it together, tidies the output (dedup, grouping by changepoint count), and
  stores it in the slot.

## 4. Validation and testing

* **Against the research prototype:** on 4 datasets by 3 confidence levels, the
  ported code reproduces the prototype's optimal changepoints, counts, budgets, per
  boundary candidate sets, and full segmentation sets exactly. Raw costs differ by a
  known constant term which cancels in every within budget comparison.
* **Against an independent oracle:** every reported gap was checked against the cost
  difference computed from raw data with hand written formulas, 1,138 segmentations
  across 10 configurations (plain and MBIC, several penalties and levels), matching
  to 1e-13.
* **Mock based unit tests:** a
  [pure R re implementation of the PELT capture](https://github.com/ArslanBatyrov/changepoint_confidence_intervals/commit/9dc1339)
  serves as a reference for the C output; the C engine and the mock agree on real data. I am not sure whether I shall keep this pure R PELT implementation that I used to test the results I get from the PELTC itseld. It is a great test, however it might be too many extra lines of code.
* **The suite:** the full package suite passes, 10,053 assertions, 0 failures, of
  which 293 assertions in 26 blocks were written for this feature (core math, public
  API, caching, printing, error guards, edge cases, property checks CS1 and CS6 from
  the paper's desirable properties list).
* **Zero regression:** the default path is byte identical to the released package.

## 5. A finding, raised with my mentors and resolved

While testing I noticed that the confidence set stops growing once the confidence
level rises past a certain point, even though the reported budget kept climbing. I called this a "Pruning Problem"" in my own head:

```
PELT pruning penalty = 17.11

level        budget    set size    max gap
0.95         13.93     14          13.83
0.99         17.15     26          17.00
0.999        21.75     26          17.00
0.99999      30.96     26          17.00
0.9999999    40.17     26          17.00
```

The budget quadrupled and the set did not move past 26.

I traced the cause. Candidates are captured *after* PELT's prune, and the prune's
slack is the detection penalty, so once the budget exceeded that slack the set was
asking for candidates PELT had already discarded. I checked this was not something my
port introduced: the research prototype captures with the identical prune condition,
and it contains a commented out line that would clamp the budget to the penalty,
which is exactly this boundary. First, I spent lots of time trying to udnerstand the issue, the find the fix to this issue, 
the try to find a better fix to this issue, the finally I asked Owen about it including whether that line had been commented out deliberately.

**Owen's answer showed me it was not even a defect!** Two reasons.
First, anything PELT prunes can never be optimal later, so it does not belong in a set
of plausible segmentations regardless of how large the budget is. Second, a level such
as 0.999999 should not keep growing the set: it would amount to asking to treat almost
every point as a possible changepoint. If 0.95 or 0.99 has already captured everything
plausible, a larger budget should not manufacture more members.

He also ruled out my irrational
proposal of measuring the effect with Segment Neighbourhood (that has a different complexity), since that method is far
more computationally expensive and would not scale! So, it turned out to be simpler that I expected and it would be way better next time to ask immediately, just a good lesson for me.

The agreed fix was to enforce `min(prune_penalty, threshold_penalty)`, which is the
prototype's commented out line switched on. It is one line in `cs_core`:

```r
cs.penalty = min(cs.penalty, penalty)
```

After the change the budget stops at the pruning penalty (17.11 above) instead of
climbing to 40.17, so the ceiling is now visible in the reported budget. Levels below the penalty are completely unaffected: 0.95 still reports 13.93
with 14 members.

I have kept this section in the report because the process, noticing the behaviour,
tracing it to a single comparison in the C loop, checking it against the prototype, noticing the commented out line,
finally raising it with a question, and implementing the mentor's decision, was one
of the more valuable parts of the project for me.

## 6. State of the work

* **Complete and working:** everything described in sections 2 to 4, on the fork's
  `main` branch, with tests and help pages.
* **Not yet merged upstream:** the work lives on my fork. Upstreaming into
  `rkillick/changepoint` is planned after my mentors' final review (Rebecca is the
  package maintainer, so this follows her release process).
* **Known limitations stated:**
  * The confidence budget formula was derived for the Normal case (as I mentioned above). The other
    distributions run and are within budget internally consistent, but their
    statistical calibration is provisional and flagged as such in the documentation
    (mentor review planned after the program).
  * The confidence set does not grow past the point where the budget reaches the PELT
    pruning penalty. This is intended behaviour rather than a limitation of the
    implementation, and is now explicit in the reported budget (section 5).
  * Sets are stored under `as.character(level)`, so `level = 0.90` is stored under
    `"0.9"`; asking for `[["0.90"]]` returns NULL. A key normalisation is a known
    small follow up. (I will hopefully fix this by the end!)

## 7. What remains (future work)

1. **Statistical validation of the budget beyond the Normal case.** The formula was
   derived for Normal data. Exponential, Gamma and Poisson run through the same code
   path and are internally consistent, but their calibration needs either a simulation
   study or exponential family theory. Rebecca plans to look at this after the program.
2. **Upstreaming.** A pull request into `rkillick/changepoint` once my mentors have
   finished reviewing.
3. **Smaller items.** Level key normalisation so `0.90` and `0.9` resolve to the same
   entry; the endpoint convention question (segmentations currently include `n`, which
   matches the prototype but not the package's own `cpts()`); and CROPS support, which
   is currently rejected with a clear error because a `cpt.range` object carries a
   penalty range rather than a single value.
